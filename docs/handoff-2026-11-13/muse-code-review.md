## 2. FINDINGS

**1. [READING] No single-instance guard on the virtual MIDI port or PID file — a second `run` silently corrupts the first.**
`src/elfjamalong/cli.py:71-96,271-328`; `src/elfjamalong/midi_out.py:13`. `cmd_run` never checks whether `PID_FILE` names a live process before opening a second virtual port also named "ElfJamAlong" (`mido.open_output(..., virtual=True)`). Failing scenario: Garth double-clicks `ElfJamAlong.command` while a terminal instance is running (the handoff itself warns there is one port and one pid file). Live now sees two identically-named ports, both instances play notes into it, `_Capturer.__init__` overwrites the PID file so `elfjamalong capture` signals only the newest, and when the first instance exits its `close()` unlinks the second instance's PID file — capture then reports "not running" while music is still playing.

**2. [CONFIRMED] No MIDI channel range validation — `--split-channels` (or `--channel 0`) crashes the realtime loop on the first note of a later role.**
`src/elfjamalong/cli.py:66,473`; `src/elfjamalong/midi_out.py:26-40`. Channel is computed as `args.channel + ROLES.index(role)` with no bounds check, and argparse accepts any int. Ran: `mido.Message('note_on', note=60, velocity=90, channel=ch)` raises `ValueError: channel must be in range 0..15` for ch = −1, 16, 17. Failing scenario: `--channel 15 --preset trio --split-channels` starts cleanly, the lead (ch 15) plays, and the first bass note (ch 16 → wire 16) throws inside `run_realtime`, killing the process with a traceback instead of a startup error. Same for `calibrate --channel 17` (`cli.py:371`, `midi_out.py:12`).

**3. [CONFIRMED] `MidiChords` never recomputes the chord on note-off — the chord goes stale as notes are released; sustain pedal is ignored entirely.**
`src/elfjamalong/midi_in.py:57-77`. `feed` recomputes `chord_from_notes` only on `note_on`; the `note_off` branch just pops `_held`. Ran with a fake clock: feed C4+E4+G4 → chord `C`; feed note_off E4, G4 (only C still held) → `chord still: C`, `_held: {48: 80}`. The engine keeps improvising over C major while the player holds a single C (or an open fifth). Related: CC64 is never looked at, so a keyboard player using the sustain pedal loses notes from `_held` the moment keys lift, even though the chords are still sounding.

**4. [CONFIRMED] `calibrate` mis-measures whenever the instrument's tail is still above threshold when the next test note is sent — it reported 5 ms for a true 120 ms delay.**
`src/elfjamalong/calibrate.py:17-26`; `src/elfjamalong/cli.py:380-385`. `onset_delays` takes the *first* block ≥ a single global threshold (`floor + 0.25·(peak − floor)`) after each send, and notes are spaced only 0.6 s apart, so a ringing guitar/piano/reverb tail from the previous note qualifies as the "onset". Ran synthetic blocks (true attack 120 ms late, previous-note tail at 0.08 vs threshold ≈0.051): returned delays `[0, 5, 5, 5, 5, 5, 5, 5]` ms and summary said `try --offset-ms 5`. The user would then play ~115 ms late while trusting the measurement. The global peak has the mirror-image flaw: one loud extraneous noise raises the threshold for all 8 notes.

**5. [CONFIRMED] Capture/render history keeps a note's full planned length when it is audibly cut short by the next note — captured MIDI overlaps and does not match what was heard.**
`src/elfjamalong/engine.py:110-118` vs `122-130`. The new `_shorten_last` is only called on the dissonant-chord cut path (`engine.py:107-109`); on a normal retrigger, `v.release()` sends the note-off but the `PlayedNote` in `history` keeps its original length. Ran a fake generator (note of 16 steps at step 0, new note at step 1): sink log was `[('on',72), ('off',72), ('on',74)]` but history was `[(72, 0.0, 4.0), (74, 0.25, 1.0)]` — the first note "lasts" 4 beats in the capture file. This is routine, not exotic, for `--lead model`: `src/elfjamalong/learned.py:143` picks lengths from `DURATIONS` (up to 16 steps) independently of when the next note starts. `capture` files and `render` output (both built from `history` via `capture.midi_file`) inherit the overlaps.

**6. [CONFIRMED] Own-note masking has no refcount — when two voices share a pitch, the first voice's note-off unmasks the pitch while the second voice is still sounding it.**
`src/elfjamalong/chords.py:218-235`; `src/elfjamalong/cli.py:256-268`. `_own` is keyed by pitch alone. Lead (60–84) and arp (52–76) ranges overlap, so both can hold, say, pitch 60. Ran: `own_note_on(60)` twice, one `own_note_off(60)`, clock advanced 1.0 s → `_own_pitches(every_voice=True)` returned `[]` and the entry was deleted, although no off was ever recorded for the second holder. After the 0.4 s tail that pitch's harmonics stop being discounted in `_analyse`, i.e. our own sustained note starts counting as evidence the *player* is playing — the self-feedback the own-note machinery exists to prevent.

**7. [CONFIRMED] `MidiChords.active()` measures the tail from the last note-*on*, not from release — a long-held chord stops the engine the instant it is released.**
`src/elfjamalong/midi_in.py:61,82-85`. `last_heard` is set only on `note_on`; `active` is `bool(_held) or clock − last_heard ≤ tail`. Ran with fake clock: chord held from t=0 to t=10 → `active(4)` True while held, and False *immediately* on release at t=10, despite `--tail 4.0` promising 4 s of grace after the player stops. For short holds the effective tail is silently eroded by the hold duration. (The existing test at `tests/test_elfjamalong.py:653-676` doesn't catch this: its simulated holds are shorter than the tail.)

**8. [CONFIRMED] `ProgressionTracker` back-fills skipped steps with the chord reported at the landing step, fabricating agreement.**
`src/elfjamalong/loop.py:64-69`; engine allows step jumps of up to 4 (`src/elfjamalong/engine.py:86`). `update` writes `heard` into every step from `_last+1` to `step`, but it is called once per engine tick with only the *current* chord. Ran: `update(0, Am)` then `update(3, F)` → `_heard = {0:'Am', 1:'F', 2:'F', 3:'F'}` — steps 1–2 are recorded as F although F was first reported at step 3. Those fabricated steps feed `_find_loop`'s 85 % agreement count and `_lag`'s change-point detection, so after any stall/Link correction the tracker can lock onto a loop earlier, and with a shifted lag, than the evidence justifies.

**9. [READING] `_HelperSource` waits forever for `rate=` and startup failures leak the helper process; `calibrate`'s prompt sits outside its try/finally.**
`src/elfjamalong/cli.py:154-169,271-283,363-391`. The constructor loops on `stderr.readline()` with no timeout. linktap only prints `rate=` when the first audio buffer arrives (`tools/linktap/main.cpp:145-148`), so a selected-but-silent Link Audio channel (sender connected, transport stopped) hangs `elfjamalong run` indefinitely before signal handlers are even installed. If the user Ctrl-Cs there — or at `calibrate`'s `input("Press Enter…")` at `cli.py:376`, which is *before* the `try:` at line 378 — or if `MidiOut()`/`_clock()` raises after `_source(args)` at line 274, nothing closes the helper: a silent linktap stays in its sleep loop (`main.cpp:167-170`) holding a Link Audio session after the parent is gone.

**10. [READING] Both helpers do blocking stdio writes on realtime audio callbacks.**
`tools/linktap/main.cpp:149,160-164` (the `LinkAudioSource` callback resizes a `std::vector` and calls `fwrite` + `fflush(stdout)`); `tools/livetap/main.swift:106,128-131` (the `AudioDeviceIOProc` block reallocates `mono` when frames grow, `fwrite`s, `fflush`es, and calls `exit(0)` from inside the callback on a short write, skipping `cleanup()`). The Python consumer drains the pipe only between detector analyses (`cli.py:171-176`); a pipe holds ~64 KB ≈ 0.34 s of mono float32 at 48 kHz, so any consumer stall longer than that (GC pause, system load, a wedged status thread — see finding 13) back-pressures the audio thread itself. Mitigating evidence from my run (§3): steady-state analysis is fast (mean 0.07 ms per 46 ms hop), so this needs an abnormal stall to bite. Note: livetap is *not* modified in `ac57a92..HEAD`; I reviewed it because the prompt named it — treat this half as context, not as a regression in the two commits.

**11. [READING] linktap announces the sample rate exactly once and never notices the channel going away; the detector's sample rate is frozen at startup.**
`tools/linktap/main.cpp:136-148,167-170`; `src/elfjamalong/cli.py:281`. `announced.exchange(true)` prints `rate=` on the first buffer only, and `ChordDetector` is built once from `source.sample_rate`. If the sender restarts or the session renegotiates 44.1 ↔ 48 kHz mid-run, audio keeps flowing but every FFT bin maps to the wrong frequency and detection silently degrades — no error anywhere. If the channel disappears, linktap's main loop just sleeps forever and the Python side sees unexplained silence.

**12. [READING] The detector's own-note dict is mutated from two threads, contradicting its own documented thread model.**
`src/elfjamalong/chords.py:95-96` says "Everything shared is a single attribute write", but `_own` is a dict written by the engine thread (`own_note_on/off`, via `_TellDetector`, `cli.py:262-268`) and iterated *and mutated* (expired entries popped) by the audio thread in `_own_pitches` (`chords.py:230-234`). Losing interleaving: the audio thread snapshots an expired entry, the engine thread re-ons the same pitch (stored as `inf`), then the audio thread's `pop` removes the new held entry — that note is unmasked for its whole duration (same failure shape as finding 6, via race instead of refcount). CPython's GIL makes this rare and non-crashing, not impossible.

**13. [READING] `_Capturer.poll` can wedge permanently on a partial line of terminal input, silently disabling capture.**
`src/elfjamalong/cli.py:80-83` (unchanged in this diff, but it is the capture path the prompt asked about). `select` reports stdin readable as soon as *any* byte is available; `sys.stdin.readline()` then blocks until a newline arrives. If the user types a few characters without pressing Enter, the status/capture thread blocks inside `readline` forever: status lines freeze and SIGUSR1 capture requests (`elfjamalong capture`) are set as a flag nobody polls. The music keeps playing (engine is on the main thread), so the failure is invisible until a capture is missed.

**14. [READING] `_HelperSource` treats any stderr line that isn't `rate=`/`channel=` as fatal — one stray diagnostic line kills startup.**
`src/elfjamalong/cli.py:160-168`. The first unexpected line triggers `raise SystemExit(f"{line} {rest}")` after draining the rest of stderr. livetap links AppKit/CoreAudio, whose frameworks can emit diagnostics to stderr; any such line printed before livetap's own `rate=` (or a future helper's informational line) aborts the run with a misleading "failed to start" message that buries the real one in the drained remainder.

**15. [CONFIRMED, API-level only] `capture.midi_file(..., order=...)` silently drops every voice not named in `order`.**
`src/elfjamalong/capture.py:21`. Ran: notes for `lead` and `bass` with `order=['lead']` → tracks were `['', 'ElfJamAlong lead']` — the bass notes vanished with no error. No current internal caller passes a partial order (`cmd_render` passes exactly the roles it built), so this is a trap for the next caller rather than a live bug.
